# 开发与 QA 日志

> 记录关键决策、在截图审查中发现的问题以及对应修复。QA 在无 GPU 的沙箱里用 Playwright + Chromium（SwiftShader 软件渲染）
> 完成：`qa/shoot.mjs` 跑完整滚动流程，`qa/quick.mjs` 只截指定位置，`qa/fps.mjs` 记录帧时间，`qa/auto.mjs` 核对自动浏览。截图不入库。

## 0. 调研（见 research.md）

- 核对了伦敦国家美术馆版（1888 年 8 月）的基本事实、书信 666/740/743/765/806 中关于「黄色高音」与向日葵系列的原文。
- 颜料科学：铬黄（PbCrO₄·PbSO₄）在光照下还原为 Cr(III) 而变暗变绿（Monico 2015；Vanmeert 2018；npj Heritage Science 2021），
  画中红色色淀（red lake）褪色 → 这成为「时间之光」老化模拟的依据（艺术化，而非精确复原）。

## 1. 资产（见 pipeline.md）

- 先生成带景深的完整主画，再用 edits 端点拆层；背景层要求补画被遮挡的墙面与桌面。
- 模型 edits 时会重新取景，肉眼几乎看不出，但叠层后花束错位约 108 px → 加入 SIFT + RANSAC 配准（花束层缩放 0.859，桌面层缩放 0.575、旋转 4.9°）。
- 调色板实测：黄色像素占 90.2%，k-means 得到 33 种黄（11 个颜料家族），所以文案写「三十三种黄」而不是凭印象写「三十余种」。

## 2. 架构

- React 只负责 DOM 叙事层（章节卡片、控件、无障碍）；Three.js 渲染全部在一个 `Engine` 里，按滚动进度驱动 6 个场景状态，
  通过 `store.ts`（极小的外部 store）与 React 通信，避免每帧触发 React 渲染。
- `Diorama`：四个景深层 + 形体高度图 → 顶点位移浮雕；片元着色器里做侧光（raking light）、颜料高度、
  「颜料湿润」揭示、老化、夜景。
- `StrokeField`：约 4.8 万道（移动端更少）实例化笔触，颜色来自 33 种黄；`Sunflower`：程序化 3D 向日葵（花瓣图集 + Vogel 种子盘）；
  `PaintStudio`：独立 WebGL 画布上的厚涂模拟器（半浮点高度场 + 侧光重光照）。
- 声音：Web Audio 实时合成（无音频文件），默认静音，用户手势后才启动。

## 4. 性能笔记

- 沙箱只有 SwiftShader（CPU 光栅化），帧率不代表真机；真机 GPU 上目标 60 fps。
- 设备分级：移动端（`pointer: coarse` 或短边 < 600）减少笔触数（种子花结 233 vs 377），背景渲染目标 0.5×（桌面 0.6×），主画布像素比上限 1.6（桌面 1.75），并按实际帧时间自适应（见 §6）。
- 所有纹理为 WebP；JS 约 906 KB（gzip 255 KB），主要是 three.js；笔触布局在 Web Worker 里计算（5 KB）。
- `prefers-reduced-motion` 时不启用 Lenis 惯性平滑滚动，并关闭各类待机摆动 / 旋转动画。

## 5. 加载流畅度优化

先用 CPU profile 与 Chrome trace（`qa/load.mjs` + CDP）剖析加载与进入的全过程，找到四个问题：

1. **首屏空白**：HTML 里只有 `#root`，加载画面要等约 900 KB 的 JS 下载、解析、React 首次渲染后才出现。
2. **加载期间主线程长任务**：纹理经 `<img>` 在主线程解码并同步上传；4.8 万道笔触的布局在主线程计算；`Engine.supported()`
   为检测 WebGL 额外创建了一个上下文（约 260 ms）；`PaintStudio` 在加载期间就创建第二个 WebGL 上下文（约 800 ms）。
3. **进入后冻结**：着色器在第一次真正绘制时才编译、链接，`getShaderInfoLog / getProgramInfoLog` 阻塞主线程 2–6 s。
4. **进度跳变**：进度按「完成的步骤数」计算，大文件下载期间停住不动，随后一下跳很多。

对应修复：

- **加载画面内联进 HTML**：Vite 插件 `sunflowers-boot-screen` 在构建时把 `lib/bootLoader.ts` 生成的加载画面（233 颗种子的
  向日葵花盘 + 书法标题）写进 `index.html`，并 `preload` 加载画面用到的三种字体和 `palette.json`。React 启动后接管这块 DOM，
  不重绘 —— 浏览器画出的第一帧就是加载画面。
- **真实、平滑的进度**：82 % 来自真实字节流（`fetch` 流式读取，总量用构建时注入的文件大小 `__ASSET_BYTES__`），18 % 来自
  GPU / CPU 准备步骤；显示值以「临界阻尼 + 最低速度」追赶真实值，种子一颗颗点亮，不跳也不停。
- **下载与解码前移、离开主线程**：bundle 一执行就发起全部下载（`prefetchScene()`，早于 React 渲染）；纹理用
  `createImageBitmap` 在后台线程解码（Safari < 17、Firefox < 98 回退到 `<img>.decode()`），每帧最多上传一张；笔触布局移到
  Web Worker（`strokes.worker.ts`，纯函数在 `strokeData.ts`，不支持 Worker 时回退主线程）。
- **着色器在加载期间预热，且不阻塞**：每个场景在自己的纹理到齐后立即构建，`compileAsync` 之后用 WebGL2 fence
  **非阻塞地**等 GPU 进程完成链接，再以 8×8 视口向它将来真正使用的目标（多重采样画布 / 背景渲染目标）画一次，让驱动把管线
  建好，然后再等一次 fence。生产环境关闭 three.js 的 `checkShaderErrors`（每个程序一次阻塞往返）。没有
  `KHR_parallel_shader_compile` 的浏览器（包括 SwiftShader）受益最大。
- **第二个画布推迟**：`Engine.supported()` 不再创建上下文；`PaintStudio` 在门页空闲、主画布 GPU 队列清空后才创建（或滚动接近
  时）；进入后的 3.2 s 开场动画期间不做任何预热步骤。
- **门页静止**：加载画面后面的场景只画 2 帧就暂停渲染，直到访客进入 → 门页上的按钮动画始终流畅。
- **退场动画修复**：种子向外迸散 + 旋转的退场此前被常驻的旋转动画覆盖、实际不播放，现在由外层包裹元素承担。

**画质与艺术性不变**：`qa/texcheck.mjs` 证明 10 张纹理在新旧两条解码路径下**逐字节一致**（含半透明图层：不做颜色空间转换、
不预乘 alpha、翻转方向一致）；mipmap、各向异性 4×、重复/镜像等采样参数，着色器、笔触数量、像素比上限都没有改动；新旧两版在
同一滚动位置的截图构图、色彩、纹理一致（差异只来自动画相位）。

## 6. 运行时流畅度优化

目标：滚动与交互时每帧更省、更稳，画面（着色器、纹理、笔触、构图与编排）一处不改。先用 `qa/smooth.mjs`（Chrome trace，
按帧拆分主线程：脚本 / 样式 / 布局 / **被脚本强制同步的**样式与布局 / 绘制 / GC）逐个场景剖析，找到三个问题：

1. **每帧强制同步布局**：`Engine.measure()` 每帧对 6 个章节逐个 `getBoundingClientRect()`，中间穿插写 CSS 变量——每读一次，
   浏览器都得先把刚写下的样式和布局同步算完（layout thrashing）。滚动越快越重。
2. **写一个变量，整章重算样式**：`--p / --e / --l` 写在 `<section>` 上、`--scroll` 写在 `<html>` 上，而自定义属性默认继承，
   每变一次整章（`--scroll` 则是整页）的后代都要重算；真正读这些变量的其实只有 8 个元素。
3. **自适应分辨率只降不升，还会误判**：旧规则每 90 帧平均超过 26 ms 就把像素比降 0.25，永不回升。浏览器被限到 30 Hz
   （省电模式）、CPU 受限、或者一阵短暂的后台负载，都会让清晰度白白降下去且回不来；真正吃力的设备又要先卡好几秒才降到位。

做法：

- **几何缓存**：各章节在文档中的位置与高度只在尺寸真的变化时重读（`ResizeObserver` 观察各章节与 `body`，外加窗口 resize），
  每帧只读一次 `scrollY` 推算各章进度；所有读取在前、写入在后，不再触发强制布局。
- **变量精准投递**：读滚动变量的 7 个元素标上 `data-vars`（如 `data-vars="e l"`），进度条加 `id="scroll-progress"`，引擎只写到它们
  身上，值没变就不写；`styles.css` 用 `@property` 把四个变量注册为**不继承**的 `<number>`，一次写入只重算一个元素。
  每帧也不再分配闭包。
- **分辨率调度器** `src/gl/governor.ts`（纯逻辑，`qa/governor.mjs` 可离线回放）：
  - 每 30 帧评一次。「迟到帧」按显示器自己的节奏判定（1.5 个刷新间隔，至少 25 ms）；刷新间隔在门页空闲时实测，再用最快的几帧
    校正，所以被限到 30 Hz 的浏览器不会被当成 GPU 太慢。
  - 连续两个慢窗口 → 沿网格降一档（桌面 1.75 · 1.5 · 1.25 · 1），下一个窗口验收：明显变快就保留；没变快就再降一档；降到底仍
    不见效，说明瓶颈不在像素（CPU 受限或浏览器限帧）——立刻恢复原清晰度，把这个节奏当作设备本身的节奏，之后的尝试按
    45 s → 5 min 退避。
  - 连续 8 个平稳窗口 → 试升一档；试升期间一旦攒到 8 个迟到帧就立即退回，一次失败的尝试只花几帧，而不是几秒的卡顿。
  - 每个章节记住自己负担得起的档位：回到吃力的章节时直接到位，不必先卡一下；在该章节失败过的档位隔一段时间再试
    （30 s 起，每失败一次加倍，最长 4 min；试成功即重置）。
  - 新档位在绘制之前生效，换分辨率不会清掉已经画好的一帧；URL 指定了 `?dpr=` 或在录制成片（`?capture`）时不调度。

实测（`node qa/smooth.mjs desktop <url> 0.25`：1440×900，像素比压到 0.25，让软件 GPU 几乎不占时间，主线程开销才看得清；
新旧构建各跑两轮取平均，单位为每帧毫秒）：

| 场景 | 主线程合计 旧 → 新 | 其中脚本 | 被强制同步的样式 + 布局 |
|---|---|---|---|
| 首屏：指针游走 | 11.3 → 12.8（噪声范围内） | 4.9 → 4.7 | 0.54 → 0.24 |
| 首屏 → 「三十三种黄」（平滑滚动） | **19.0 → 12.6** | 10.4 → 4.5 | **8.05 → 0.73** |
| 「三十三种黄」：横扫色带 | 3.8 → 3.5 | 1.4 → 1.2 | 0.14 → 0.11 |

  指针游走、横扫色带这类本来就不重的场景持平。
- 沙箱只有 SwiftShader，fps 没有意义（GPU 一帧要几百毫秒），只比较主线程毫秒；真机上省下的正是滚动时最容易掉帧的那部分。

| 同一章节短暂吃力 8 s | 1.13 · 1.4 %（回不来） | 1.55 · 0.7 %（负载过去约 35 s 后回到全清晰） |
| 吃力章节 → 轻松章节 | 1.05 · 5.5 % | 1.33 · 2.5 % |
| 吃力 / 轻松章节每 20 s 交替 | 1.26 · 1.0 % | 1.39 · 0.6 % |
| 完整浏览一遍（各章轻重不一） | 1.29 · 1.7 % | 1.49 · 1.5 % |

接入后在浏览器里也实测了一遍（320×200、2× 屏，不指定 `?dpr`）：SwiftShader 用 CPU 渲染，降分辨率解决不了问题，调度器
1.6 → 1.35 → 1.1 → 1 试探无效后恢复 1.6，并把这个节奏认作设备本身的节奏，此后不再反复试探；全程无报错。

画质不变的依据：

- 着色器、纹理、笔触、像素比上限（桌面 1.75、手机 1.6、约 3.4 MP 像素预算）和全部编排曲线都没有改动；
- 新旧构建在 14 个滚动位置上逐一比对：所有读滚动变量的元素，计算出的透明度与变换逐字相同；引擎拿到的各章进度
  （rel / len）也完全相同（差值为 0）；
- 跟得上的设备分辨率从不改变；只有真的跟不上才降，而且会回升——旧规则降了就再也回不来。

## 7. 自动浏览（自动模式）

一份分镜，两种播放：[`src/auto/storyboard.ts`](../src/auto/storyboard.ts) 是唯一的分镜（滚动关键帧、光标路径的锚点、7 次按下/抬起
的时刻，全长 63.6 s），[`src/auto/autopilot.ts`](../src/auto/autopilot.ts) 在页面里逐帧播放它——真人录屏时跟着真实时钟走，
`qa/record.mjs` 拍成片时跟着虚拟时钟走，两边是同一场演出。

- **驱动**：挂在引擎的 `beforeFrame` 上（先于 Lenis），每帧按分镜算出滚动与光标位置；滚动用
  `lenis.scrollTo(y, { immediate, force })`；帧间隔上限 0.25 s，标签页切走再回来不会跳拍。
- **像真鼠标一样**：光标每一步都派发合成的 `PointerEvent`：先用 `elementsFromPoint` 命中测试（跳过挡板），补齐
  out / leave / over / enter 边界事件，按下、抬起后在共同祖先上派发 click。网站自己的悬停、点击、按住、拖动代码照常响应，
  没有为自动模式写特例。三处补丁：年代滑块按拇指位置换算数值，经原生 value setter 写入并派发 `input` / `change`；
  合成事件不触发 `:hover`，改为给光标下的控件打 `data-hover`，CSS 镜像悬停样式；合成指针不能 `setPointerCapture`
  （会抛错），`PaintStudio` 里改为 try/catch。
- **落点**：锚点按实时布局取（花心、色带、按钮、滑块……），不写死像素，其他屏幕尺寸也能对位；「点花」取引擎给出的第一朵
  不在界面元素上的花；画面静止时的定点若落在按钮、链接、表单控件或 `[data-ui]` 上，会被挪开，避免误点。
- **挡板**：播放期间全屏透明的 `#auto-shield` 吞掉真实的指针、鼠标、滚轮、触摸和滚动键，误碰不会打乱录制；真实的点击或
  滚动只会让底部浮出「自动浏览中 · 点此或按 Esc 退出」（3.2 s）。<kbd>Esc</kbd> 随时退出，正在按住的也立即松开。
- **向日葵光标与点击波纹**：光标换成一朵 SVG 向日葵（两圈参差的尖花瓣、每瓣一笔提亮、普鲁士蓝描边的赭褐花盘、按黄金角
  排布的花籽），轻轻摇摆，并顺着运动方向倾斜（`--lean`）；按下时低头旋转，按住时套上一圈光环；尺寸沿用网站光标的状态
  （界面上 0.88×、花上 1.3×、耙光 1.35×）。画面本身满是黄色，所以花瓣描边加深，外轮廓再加一道发丝细的普鲁士蓝，
  在画上、铬黄底和奶油色卡片上都看得清。每次点击在 `#auto-fx` 上放一圈铬黄波纹和 8 片飞散的花瓣。
- **进入与退出**：门页「▶ 自动浏览 · 约 1 分钟」或按 <kbd>A</kbd>；页眉和尾声的按钮（不在顶部时先用 1.2–4.2 s 滑回开头，
  并复位螺线、选定的黄和年代）；录屏地址 `?auto` 让门页两个进入按钮直接开始；`?auto=loop` 播完停 2.5 s、清空画布，
  再从头播放。结束时有 0.75 s 的谢幕：光标淡出，原来的光标与页面交还给访客。
- **字体**：新文案里的「约」「钟」不在 Noto Serif SC 子集里，只重新子集化了这一款（其余三款不动），并重新编码 `assets-encoded/`。

QA（`node qa/auto.mjs`，1920×1080，虚拟时钟 10 fps），20 项全部通过。整段导览：耙光按住即开、松开即关；点花响起和弦（4 个音）；
色花回应悬停；色带扫出 12 种黄；螺线打开；年代拖回 1888 再拖到 0.59；选中普鲁士蓝；画出两笔普鲁士蓝（画布 2.2 % 的像素变蓝；
画布同时在自己「种」一朵向日葵，所以只数蓝色）；六章依次经过；7 次按下都看得见；播完谢幕、交还页面（全程 64.5 s，645 帧）。
其他路径：从尾声点页眉按钮，会先滑回顶部再播放；误点只浮出提示，滚轮滚不动；按住途中按 Esc 立即松开并交还；无控制台报错。
1280×720 下复核前 14 s（`--to=14`）：耙光与点花都落在画上，没有点到首屏卡片。

## 8. 演示成片

`qa/record.mjs` 以 `?capture&auto` 打开构建好的网站，只在门页点「带声音进入」，之后的六章交给自动浏览（§7）按同一份分镜播放，
逐帧录制（详见 [demo-film.md](demo-film.md)）。`qa/capture-clock.js` 接管时钟（`performance.now`、定时器、rAF、CSS 动画），
每帧精确前进 1/30 s，所以软件渲染再慢，成片也是匀速 30 fps；声音不实时播放，而是记录下每个音符的时间，最后用同一套合成器在
`OfflineAudioContext` 里渲染成配乐。

## 9. 已知限制

- 画面是 AI 再创作，不是原作；老化/复原效果是基于研究方向的艺术化模拟，不是逐像素的科学复原。
- `PaintStudio` 在不支持半浮点渲染目标的旧设备上退化为 8 位高度场，浮雕会更平。
- 不支持容器查询单位的旧浏览器（如 Safari 16 以前）中，标题会回退为样式类里的固定字号。
